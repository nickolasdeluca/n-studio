# Script Executive: implementation plan

A plan, not yet built. It is written for whoever implements it next, with
no memory of the conversations that led to it: what is asked, what the
repository already has, what is missing, in which order to build it, and
what was left for the owner to decide.

Read `AGENTS.md` first. Its rules bind this work in two places in
particular: nothing learned from a real database goes into the repository
(the scripts and the CONNECT lines the owner showed as examples had a real
server, path and password in them; none of that is repeated here, and none
of it belongs in a test), and everything that writes is tried only against
the docker fixture, behind `FB_FIXTURE=1`.

## 1. What is asked

Parity with IBExpert's Script Executive: a tool for running large scripts
made of many statements, all of them or only some, from the editor or
straight from a file. The owner's scripts are generated by tools and look
like this, each statement wrapped in its own `SET TERM` pair and closed by
a line of dashes (which is an SQL comment):

```sql
SET TERM ^ ;
ALTER PROCEDURE NORMALIZA_TEXTO (ENTRADA VARCHAR(100))
RETURNS (SAIDA VARCHAR(100))
AS
BEGIN
  SAIDA = UPPER(ENTRADA);
  SUSPEND;
END
^
SET TERM ; ^
------------------------------------------------------------------
SET TERM ^ ;
COMMIT WORK
^
SET TERM ; ^
------------------------------------------------------------------
```

A **block** is one statement of the script, with the `SET TERM`s and
comments around it. `fb_sql::split` already yields exactly that.

What IBExpert's tool has, and so what parity means (its screens were shown
for analysis only: the behaviour is the reference, the layout is ours):

| IBExpert | What it does |
|---|---|
| Script page | The script's text, with the statement being run or failed marked |
| Statements page | Every statement as a row with a checkbox: run only the checked ones |
| Options page | Stop on error, how DDL is committed, what happens to the transaction at the end |
| Messages (Line, Message) | What failed and where; a click goes to the line |
| Script explorer | A tree by object kind (Tables, Procedures, Triggers, …) of what the script touches, each with its operations (`Alter X`, `Comment X.COL`), built without running anything; a click goes to the statement |
| Run Script (F9) | Runs the text in the editor |
| Run from file (Shift+F9) | Runs a file without loading it into the editor: for scripts too big to edit |
| Stop Script | Stops before the next statement, and cancels the running one |
| Add CONNECT statement | Asks which registered database and writes `SET NAMES`, `SET CLIENTLIB` and `CONNECT … USER … PASSWORD …` at the top |
| Connection selector | "No active connection" or a registered database |
| Execute charset | The character set the script's text is sent in |

## 2. What the repository already has

Do not rebuild these; extend them.

- **Splitting**: `crates/fb-sql/src/lib.rs`, `split(text) -> Vec<Statement>`
  follows `SET TERM`, tells `Sql` from `SetTerm` and `Isql`, and gives byte
  ranges. `utf16_offset`/`byte_offset` convert for the editor.
- **Running**: `crates/fb-core/src/script.rs`, `run_script(conn, tx,
  tx_options, text, options, cancel, on_step)`: statement by statement,
  `SET AUTODDL`, commit after DDL, `stop_on_error`, `atomic`, cancel flag,
  a `Step` per statement with its outcome (`Done`, `Skipped`, `Failed`).
  Other isql commands are skipped.
- **The command**: `src-tauri/src/script.rs`, `script_run` and
  `script_cancel`, progress as `script-progress` events carrying only what
  failed, on the registration's shared session.
- **The editor's own script run**: `ui/src/editors.ts` `runScript` and the
  toolbar's "Execute as Script (Ctrl+F9)" in `SqlEditor.tsx`. It stays as it
  is: the quick way, inside an editor. The Script Executive is the tool for
  scripts as work in themselves.
- **Files**: `src-tauri/src/files.rs`, `script_read`/`script_write` with
  encoding detection (UTF-8, BOM, UTF-16, WIN1252) and CRLF kept; refuses
  more than 32 MB, because the text goes to the UI.
- **A connection of one's own**: `src-tauri/src/trace.rs` opens a dedicated
  `Connection` from `state.params(id)` for the monitor's sampler. The Script
  Executive needs the same: a long script must not queue behind the editors,
  nor they behind it.
- **Passwords**: `src-tauri/src/secrets.rs` (keychain) and the UI's
  `password` dialog (`store.ts` `Dialog`), used by `connect`.
- **Panels**: `ui/src/dock.ts` and, as the model of a tool panel with its
  own store and tabs, `ui/src/monitor.ts` + `ui/src/components/ActivityMonitor.tsx`.
- **Virtualized lists**: `@tanstack/react-virtual`, as `ResultGrid` and the
  monitor's Live tab use it.
- **Looking at the UI without the app window**: the temporary preview
  (memory `ui-visual-check`): recreate the mock from history, extend its
  `command()`, drive it with puppeteer, delete it afterwards.

## 3. What is missing

### 3.1 `fb-sql`: what a statement is about

New, pure, unit-tested: `classify(sql) -> Subject`, from the statement's
first tokens only (the lexer is there; no parser is needed, and what is not
recognised is `Other`, never an error).

```rust
pub struct Subject {
    pub operation: Operation, // Create, Alter, CreateOrAlter, Recreate, Drop,
                              // Comment, Grant, Revoke, Insert, Update, Delete,
                              // Merge, Select, Execute, Commit, Rollback,
                              // SetGenerator, Connect, Other
    pub kind: Option<ObjectKind>, // Table, View, Procedure, Function, Package,
                                  // Trigger, Domain, Generator, Exception,
                                  // Index, Role, User, Udf, Database, Block
    pub name: Option<String>,     // as the catalog stores it (fb-sql already
                                  // has the rule: quoted as written, else upper)
    pub member: Option<String>,   // the column of COMMENT ON COLUMN T.C,
                                  // the table of CREATE INDEX … ON T
}
```

Rules worth writing down before coding them:

- `CREATE [OR ALTER] | ALTER | RECREATE | DROP <kind> <name>`; `CREATE
  [UNIQUE] [ASC|DESC] INDEX i ON t` files under table `t` with member `i`,
  and also under Indices.
- `COMMENT ON <kind> <name>` and `COMMENT ON COLUMN t.c` (under table `t`).
- `INSERT INTO t`, `UPDATE t`, `DELETE FROM t`, `MERGE INTO t`: under table
  `t`, operation the DML verb. `UPDATE OR INSERT INTO t` too.
- `EXECUTE PROCEDURE p` under procedure `p`; `EXECUTE BLOCK` is a
  "Firebird block", a group of its own as in IBExpert.
- `GRANT … ON <kind> name` / `REVOKE …` under that object; `GRANT role TO`
  under Roles.
- `ALTER SEQUENCE g`, `SET GENERATOR g TO n` under Generators.
- `COMMIT`, `COMMIT WORK`, `ROLLBACK`: no object; they show in the
  Statements list and not in the tree.
- IBExpert's own `DESCRIBE <kind> name 'text'` is in old scripts: recognise
  it as `Comment` on that object, and see 3.2 for running it.

The isql commands the runner must understand get a small parser beside it
(`fb_sql::isql::command(sql) -> Command`): `Connect { database, user,
password, role }`, `SetNames(charset)`, `SetAutoDdl(bool)`,
`SetSqlDialect(n)`, `SetClientLib` (ignored: the client is this app's own
Rust one), `Input(path)`, `Other`. `set_auto_ddl` in `fb-core/src/script.rs`
moves there.

### 3.2 `fb-core`: a runner that can do what the tool needs

`run_script` grows, or gets a sibling, so that:

1. **A subset can run**: `only: Option<&[usize]>` (statement indices as
   `split` minus `SetTerm` counts them, which is what `Step.index` already
   is). Statements not chosen are not run and not reported. isql commands
   that set state (`SET AUTODDL`, `SET NAMES`, `CONNECT`) are statements
   like the others: they apply only when chosen. The UI checks all by
   default and offers "run from here", so the common cases need no thought.
2. **`CONNECT` works**: the runner is handed a way to get a connection
   rather than a connection (`trait Connector { fn connect(&mut self,
   target: &Connect, charset: Option<&str>) -> Result<Connection> }`), holds
   the current one itself, ends the active transaction the way the options
   say before switching, and fails every statement with a clear message
   while there is none ("No connection: choose a database or start the
   script with CONNECT"). `SET NAMES` before a `CONNECT` is the charset of
   that connection.
3. **Every step is reported**, not only failures: the Statements tab shows
   each row's state, time and affected rows. Batch them as `script.rs`
   batches problems (100 ms, or 200 steps).
4. **`DESCRIBE`** is sent as the `COMMENT ON` it means. Optional; drop it if
   it complicates the loop.

The transaction rules stay isql's: DDL committed as it runs unless
`SET AUTODDL OFF`; `COMMIT`/`ROLLBACK` in the script end the transaction;
what is still active at the end is handled by the option in 3.5.

### 3.3 `src-tauri`: a run of its own

New module `src-tauri/src/executive.rs`, modelled on `trace.rs`:

- `Executives` in `AppState`: runs by id, each with its cancel flag, its
  own `Connection` (opened from `state.params(registration)` when the panel
  has a database chosen, or by the script's `CONNECT`), and the transaction
  it left active, if any.
- `executive_outline(text) -> Vec<Block>`: `split` + `classify`, for the
  Statements tab and the explorer. `Block { index, from, to, line, lines,
  kind, subject, summary }`, offsets in UTF-16 as `sql_statements` gives
  them, `summary` the first 120 characters on one line.
- `executive_outline_file(path)`: the same for a file, returning the blocks
  only, never the text.
- `executive_run(run, registration: Option<String>, source: Text(String) |
  File(PathBuf), only: Option<Vec<usize>>, options)`: runs on a thread of
  its own (not through `blocking` on the shared session), emits
  `executive-progress { run, steps: [...], at, total }`, answers with the
  summary. For a file it reads the bytes itself, decodes them with
  `files.rs`' detection (or the charset the panel chose), and never sends
  the text to the UI.
- `executive_cancel(run)`: sets the flag and calls `Connection::cancel` on
  the run's connection.
- `executive_end(run, how)`: commits or rolls back what the run left
  active, and closes its connection.
- A `CONNECT` in the script resolves its password in this order: the
  `PASSWORD` it wrote; else the keychain entry of the registration whose
  host, port, database and user match; else an event that has the UI ask
  (the existing password dialog) and the run wait for the answer. A
  password is never logged, echoed in a message, or kept in history.

**Size.** `files.rs` refuses 32 MB because the text goes to the UI. A file
run from disk does not, so it may be larger, but `split` works on the whole
text: tokens plus a byte mask cost a few times the file's size. Start by
reading whole files up to a stated limit (256 MB), measure on a script of
that size, and only if that is too much build an incremental splitter
(`fb_sql::Splitter::feed`, the terminator state carried across chunks).
Say the limit in the UI when it is hit; do not fail in silence.

### 3.4 Add CONNECT statement

A dialog listing the registered databases; choosing one writes at the top
of the script:

```sql
SET NAMES WIN1252;

CONNECT 'server/3050:C:\data\sales.fdb' USER 'SYSDBA';
```

- No `SET CLIENTLIB`: there is no client library to name. An existing one
  in a script is skipped.
- **No password by default.** The run finds it in the keychain (3.3). A
  checkbox "Write the password in the script" exists for scripts that must
  run elsewhere, off by default and with a line under it saying the file
  will hold it in plain text. This is the one place the plan departs from
  IBExpert on purpose; see section 6.
- `ROLE 'r'` when the registration has one.

### 3.5 The panel

`ui/src/executive.ts` (store, keyed by panel id, as `monitor.ts`) and
`ui/src/components/ScriptExecutive.tsx`. Opened from the toolbar, the
registration's context menu ("Script Executive", beside Activity Monitor)
and with no database at all, which the monitor cannot do: `dock.ts` and the
panel's guard must allow a panel without a connected registration.

```
[Database: (from the script) ▾] [Open ▾] [Save] | [▶ Run F9] [▶ Run Checked] [Run from File… ⇧F9] [■ Stop] | [Explorer] | Charset: (file's) ▾      12 / 480 · 2 failed
┌ explorer ──────────┬ Script │ Statements │ Options ─────────────────────────────────┐
│ Tables (1)         │                                                               │
│  PARAMETRO (3)     │  the editor (CodeMirror, as SqlEditor builds it), with the    │
│   Alter            │  running statement and the failed ones marked in the gutter   │
│   Comment .COLUNA  │                                                               │
│   Alter            │                                                               │
│ Procedures (2)     ├───────────────────────────────────────────────────────────────┤
│ Firebird blocks    │ Line │ Message                                                │
└────────────────────┴───────────────────────────────────────────────────────────────┘
```

- **Script tab**: the editor. Extract what `SqlEditor.tsx` builds its
  CodeMirror view from (theme, dialect, keymap, completion) into a shared
  factory rather than copying it. Completion works when a database is
  chosen.
- **Statements tab**: a virtualized list, one row per block: checkbox, line,
  operation and object (from `classify`), first line of text, state
  (waiting, running, done, failed, skipped), time, rows affected. Header
  checkbox for all; "Check from here", "Check only failed" after a run. A
  click goes to the block in the Script tab; a failed row shows its error
  under it.
- **Options tab**: stop at the first error (default on, as IBExpert's
  "abort on error"); commit DDL as it runs (default on); at the end, with a
  transaction still active: ask (default), commit, or roll back; on a
  failure that stops the script: roll back what was not committed (default
  on).
- **Explorer**: the tree of 3.1's subjects by kind, counts beside each kind
  and object as IBExpert shows them, built from `executive_outline`
  (debounced 300 ms after typing; from `executive_outline_file` when a file
  is loaded for running only). A click selects the statement. Kinds with
  nothing are shown dimmed, not hidden, so the tree does not jump.
- **Messages**: Line and Message, newest last, a click goes to the line;
  the summary line at the end (run, failed, skipped, time).
- **Run from File**: a file dialog, then the outline (Statements and
  explorer fill, the Script tab says the file is being run from disk and
  shows its path and size), then the run. Nothing is loaded in the editor.
- **Closing or quitting during a run, or with a transaction left active**:
  goes through `pending.ts`, as editors do.
- **Database selector**: "(from the script)" when the script has a
  `CONNECT`, else the registered databases; changing it while a transaction
  is active asks first.

### 3.6 Keys

F9 runs, Shift+F9 runs from a file, as in IBExpert. In an SQL editor F9
already means "execute": the panel's keymap is its own, so there is no
conflict. Ctrl+F9 in an editor stays the editor's quick script run.

## 4. Order of work

One logical change per commit, each with `cargo build --workspace` without
warnings and the tests passing; push, then read the Actions run and report
it by commit and job.

1. `fb-sql`: `classify` and the isql command parser, with unit tests (the
   shapes in section 1, quoted names, comments before the first keyword,
   every rule of 3.1).
2. `fb-core`: the runner takes a subset and reports every step. Live tests
   on the fixture (`FB_FIXTURE=1`): a subset runs and the rest does not;
   `SET AUTODDL OFF` holds DDL back; stop on error stops.
3. `fb-core`: `CONNECT` and `SET NAMES` through a connector. Live test: a
   script that connects to the fixture by its own `CONNECT`, with the public
   fixture credentials.
4. `src-tauri`: `executive.rs` (outline, run on its own connection, cancel,
   end), unit tests for the outline and the password order.
5. UI: the panel's shell, Script tab, messages, Run and Stop.
6. UI: Statements tab and running the checked ones.
7. UI: the explorer.
8. UI + backend: Run from File.
9. UI: Add CONNECT statement, the database selector, the password prompt.
10. Docs: `docs/PLAN.md` gets the milestone (M10) with what it cannot do,
    `README.md` its paragraph under "Manage the server" or a section of its
    own; this file is deleted or reduced to what is still open.

Check the UI in the temporary preview before calling 5 to 9 done; it has
caught real bugs that type-checking did not.

## 5. Out of this plan

- IBExpert's own language: `IBEBlock`, `ibec_*` functions, its `IBE Blocks`
  group in the explorer.
- `SET CLIENTLIB` (skipped), `SHELL`, `OUTPUT`, `SHOW …` and the rest of
  isql's interactive commands (skipped, said so in the messages once).
- `INPUT 'file'` (running another script from inside one): parse it, report
  it as not followed; following it is a later step.
- `CREATE DATABASE` and `DROP DATABASE` from a script: they need no
  connection and the app has no path for them yet. Report as not supported.
- Parameters in scripts, and showing a `SELECT`'s rows: a script's selects
  only have to run, as today.
- Comparing the script with the database before running ("this ALTER will
  fail"): the explorer says what is touched, not whether it will work.

## 6. For the owner to decide

Defaults are chosen so that the work can go on; these are the ones that
change behaviour people will notice.

1. **The password in `CONNECT`**: the plan writes none and reads the
   keychain; IBExpert writes it in plain text. Scripts that already have a
   `PASSWORD` run as they are either way.
2. **A transaction still active when the script ends**: the plan asks, as
   IBExpert does. Always committing is what unattended runs would want.
3. **Whether Run Checked applies unchecked `SET` and `CONNECT` lines**: the
   plan says no: a statement runs only if it is checked.

## 7. Where the project stands at handover

- `v0.4.0` is published as a full release, the first with the updater. No
  install has updated itself yet, because there is nothing newer: the next
  release is what proves download, signature check and restart end to end.
  The updater's private key is on the owner's Mac
  (`~/.tauri/n-studio-updater.key`) and in the repository's
  `TAURI_SIGNING_PRIVATE_KEY` secret; it must never be regenerated.
- Releasing is in the README ("Building a release"): bump the workspace
  version, commit `Version X.Y.Z`, tag, push the tag, then
  `scripts/build-release.sh --release` on the Mac.
- Built but not exercised in the real window against a real server:
  changing a select's rows in the editor's grid (real databases are
  read-only to us; only the owner can try it on a database of theirs), the
  window's place on Windows and Linux, and the fix for the monitor's Live
  detail being cut off (it could not be reproduced in the preview).
- Replies to the owner are in Brazilian Portuguese; code, comments, docs
  and commits in English, in the plain style the history shows.
